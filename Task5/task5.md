### <a name="_qmphm5d6rvi3"></a>**Решение**

[Диаграмма контекста](context.puml)

[Диаграмма контейнеров](container.puml)

***Пояснения***

* Работа с депозитами и со ставками вынесена в отдельные микросервисы для повышения отказоустойчивости и скорости развертывания в случае проблем
* Технологии для реализации MVP выбраны с учетом опыта текущей команды (ASP.NET) и снижения зависимости от дорогостоящих решений внешних вендоров (PostgreSQL)
* Для получения данных сервисом предрасчета ставок из существующей АБС по клиентам используется REST API, так как ответ требуется получить синхронно и это не потребует подключения АБС через Kafka
* Поскольку команда утверждает, что ускорить обмен данными между АБС и кредитным конвейером невозможно, на данный момент процесс остается как есть. Его дальнейшая оптимизация будет прорабатываться отдельно
* Использован API Gateway для маршрутизации запросов, балансировки нагрузки, rate limiting и circuit breaking (требования по отказоустойчивости и толерантности к росту нагрузок)
* Обмен сообщениями между микросервисами идет через Kafka, для простоты масштабирования и реализации событийной модели обмена сообщениями (позволяет не завязываться на жесткие API между сервисами)
* Для ускорения разработки на первом этапе принято решение не выносить SMS-шлюз в отдельный микросервис - архитектура MVP позволит в случае чего быстро интегрировать его в следующую очередь

### <a name="_bjrr7veeh80c"></a>**Альтернативы**

* Один монолит для работы с кредитами и ставками
  * Плюсы: проще в поддержке для команды, не имеющей опыта с микросервисами; не требуется проработка контрактов для взаимодействия сервисов
  * Минусы: риск отказов, влияющих на весь кредитный процесс; более медленное применения правок; при масштабировании будет избыточное выделение ресурсов на менее востребованные функции
* Взаимодействие между сервисами через REST API
  * Плюсы: проще в реализации для команды, не имеющей опыта с Kafka
  * Минусы: требует более жесткой связности сервисов, в отличие от event-driven обмена через Kafka; меньше устойчивость к нагрузкам и сложнее масштабировать
* Взаимодействие с АБС через Kafka
  * Плюсы: более универсальное решение на случай, если в дальнейшем понадобится больше асинхронных взаимодействий с АБС
  * Минусы: возможно, будет лишней тратой ресурсов, так как на данном этапе нужно только синхронное взаимодействие; сложнее в реализации для команды, не имеющей опыта с Kafka

**Недостатки, ограничения, риски**

* Потребуется дополнительное обучение команды микросервисной архитектуре и Kafka, либо найм специалистов с опытом в этих технологиях
* Увеличение сложности поддержки системы за счет большего количества сервисов, необходимости внедрения DevOps-практик
* Требуется продумать согласованность данных между микросервисами и существующими системами
* АБС при высокой нагрузке может все еще быть точкой отказа, что требует планирования дальнейшего переписывания всей АБС на новую архитектуру
