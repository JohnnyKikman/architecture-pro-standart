***Пояснения***

* Функционал выгрузки ставок разумно реализовать в рамках создаваемого микросервиса работы с депозитными ставками
* Поскольку нет требования об обновлении ставок в реальном времени, и желательно сразу адаптироваться к масштабированию системы, для уведомления внутренней системы колл-центра используется Kafka. Это также открывает возможность для того, чтобы потенциально система колл-центра могла получать и другие события
* Передача самих ставок во внутреннюю систему колл-центра происходит отдельным вызовом через REST API для избежания излишней нагрузки на Kafka, поскольку запросы через REST API при желании можно маршрутизировать на менее загруженный экземпляр сервиса депозитных ставок
* Обмен данными с партнерским колл-центром производится через SFTP сервер в связи с невозможностью дорабатывать прямую интеграцию со внешней системой колл-центра
* Требуется дополнительная консультация с партнерским колл-центром для того, чтобы формат и расширение файлов со ставками были максимально удобными для загрузки в систему партнерского колл-центра
* При необходимости можно будет добавить почтовые уведомления для внешнего колл-центра, чтобы их сотрудники могли оперативнее реагировать на изменение ставок

### <a name="_bjrr7veeh80c"></a>**Альтернативы**
Опишите здесь наиболее важные альтернативные решения.

* Передача ставок во внутреннюю систему колл-центра через Kafka
  * Плюсы: меньше доработок как со стороны системы колл-центра, так и со стороны сервиса депозитных ставок; меньше нагрузка на REST API сервиса депозитных ставок
  * Минусы: размер файла со ставками может быть очень большим для охватывания всех условий; частое обновление ставок может вызвать повышенную нагрузку на message broker; сложно организовать постраничную выгрузку ставок при необходимости
* Интеграция через файловый сервер с системой обоих колл-центров
  * Плюсы: меньше доработок со стороны депозитных сервисов за счет унификации контракта для двух систем колл-центров; возможность в принципе не дорабатывать систему внутреннего колл-центра
  * Минусы: риски человеческих ошибок из-за ручного обновления ставок; более долгое обновление ведет к задержкам в актуализации данных в системе внутреннего колл-центра
* Интеграция через API с системой партнерского колл-центра
  * Плюсы: отсутствие необходимости ручного обновления ставок сотрудником партнерского колл-центра; меньше доработок со стороны депозитных сервисов за счет унификации контракта для двух систем колл-центров
  * Минусы: невозможность доработки партнерской системы колл-центра
* Отправка ставок в партнерский колл-центр через e-mail
  * Плюсы: проще в реализации, чем обмен через файловый сервер; большая информированность партнерского колл-центра об изменениях ставок
  * Минусы: риски, связанные с безопасностью банковских данных; электронная почта не гарантирует сохранение порядка доставки файлов со ставками, что приведет к несогласованности данных на стороне партнерского колл-центра

**Недостатки, ограничения, риски**

* Необходимо поддерживать два формата передачи ставок - для внутренней (через Kafka + REST API) и для внешней (через SFTP-сервер) систем колл-центров 
* Требуется максимально подробно описать контракт файлов, которые будут отправляться во внешний колл-центр, для максимальной простоты и скорости обновления данных
* Ручной обмен файлами приведет к задержкам в обновлении ставок в партнерском колл-центре
* Дополнительные затраты и требования к экспертизе для корректной настройки и поддержки SFTP-сервера
* На случай отказа основного SFTP-сервера - что парализует обновление ставок в партнерском колл-центре - требуется либо иметь запасной SFTP-сервер, либо договориться об альтернативных форматах передачи ставок для такого случая
